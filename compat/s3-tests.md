# ceph s3-tests compatibility

Generated by `python3 -I scripts/s3tests-report.py` from `compat/s3-tests/azblob-azurite.json`, `compat/s3-tests/fs.json`, `compat/s3-tests/gcs-fake.json`, `compat/s3-tests/s3-rustfs.json`. Do not edit it by hand: run `scripts/s3tests.sh <label>` for a backend, then the command above.

Each run starts a fresh s3dal on one backend and runs the whole [ceph/s3-tests](https://github.com/ceph/s3-tests) suite at [`fb8b73092bb1`](https://github.com/ceph/s3-tests/tree/fb8b73092bb1dd8db829f1205a9e52e73bf9a232), the ref s3s pins, with no marker filter.

How to read it:

- The pass rate is passed / total, and total counts every collected test, skipped ones included: a skip is not a pass, and every backend gets the same denominator.
- *failed*: the test body failed, or ran into the per-test timeout. *error*: its setup or teardown failed. *skipped*: the suite skipped it.
- s3dal has one tenant, so the suite's alt, tenant and IAM users are all the main user. ACL, policy, IAM and STS results do not measure isolation between users.
- Tests of features s3dal does not implement or deliberately refuses (versioning, ACLs that grant access, bucket policies, object lock, SSE, object tags, lifecycle, CORS, logging, POST uploads signed with SigV2, as all of the suite's are, IAM, STS, SNS, S3 Select) are expected to fail. Some pass anyway because a refusal is all they check: most s3-select tests compare the results of two queries, which match when both are refused.
- *s3dal source* is the git tree id of the source that ran, without `compat/`; for a commit it is `git ls-tree COMMIT | awk -F'\t' '$2 != "compat"' | git mktree`.
- Test ids are relative to `s3tests/functional/`, and tests are put in categories by the rules of s3s's `scripts/report-s3tests.py`.
